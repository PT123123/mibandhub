# 睡眠数据同步排查记录（睡眠页恒为 0 夜）

> **状态：✅ 根因已定位并修复 —— 睡眠判据写错了，不是数据没拿到。**
> 首次排查 2026-09-15（当时结论有误，见 §4）；真机取原始字节复测 2026-09-16 定案。
> 相关代码：`proto/ActivitySync.kt`（字节层 + 判据）、`proto/BandSession.kt`（`syncActivity` /
> `fetchActivityBlocks` / 诊断日志）、`service/ActivityDataImport.kt`（落库）、
> `debug/ActivityLab.kt`（真机取数实验台）、`tools/analyze_activity_dump.py`（离线分析）。

## 1. 现象

点「同步手环数据」后，睡眠页解析出来的睡眠一直是 **0 夜**（夜数/分钟数都没有），
但手环自己（官方 Mi Fit）能正常显示睡眠。

## 2. 根因：MB5 的「睡眠分钟」不在 kind 字节上

原实现把「睡眠分钟」判成 `kind == 0x78`（`ActivitySync.KIND_SLEEP`）。**Mi Band 5 从不给这个值**：

- `0x78` = 120 是 **华米新一代（Zepp OS：GTS/GTR 2+）** 的扩展样本格式。GB 里
  `HuamiExtendedSampleProvider.TYPE_SLEEP = 120`，而该 provider **只被 `ZeppOsCoordinator` 使用**；
- Mi Band 5 走的是 `HuamiCoordinator.getSampleProvider` → `MiBand2SampleProvider`，
  它的「睡眠」是 `rawKind & 0x0f ∈ {9 浅睡, 11 深睡}` 这一套**低半字节编号**，跟 0x78 无关；
- 实测 7 天全量（10075 分钟）里 **一个 0x78 都没有**，于是「归并出 0 夜」是必然结果。

**真正可用的判据：看分期字段有没有被填。**

8 字节样本布局 `[kind, 强度, 步数, 心率, 未知, 浅睡强度, 深睡强度, REM 强度]`，
后两个字节的**最高位 0x80 是「这一分钟没有分期数据」哨兵**（真机 3216 个样本里
byte6/byte7 恒 ≥ 0x80，一个例外都没有，说明最高位是标志位、低 7 位才是强度）：

```
清醒分钟： 50 42 00 ff 06 00 80 80     ← 浅睡 00、深睡 80、REM 80（无分期）
睡眠分钟： f0 00 00 3c 04 38 94 9c     ← 深睡 14(0x94&0x7f) 、REM 1c，分期被填
```

判据 = `deepRaw != 0x80 || remRaw != 0x80`（并保留 `kind == 0x78` 作为新一代固件的兼容）。
分期仍按 GB 的阈值：REM 强度 > 55 → REM，深睡强度 > 42 → 深睡，其余浅睡。

### 判据对比（2026-09-16，真机 3216 分钟原始字节，09-09 14:15 → 09-11 19:52）

| 判据 | 睡眠分钟 | 夜数 | 归并出的夜 | 各夜「独立佐证」 |
| --- | --- | --- | --- | --- |
| `kind == 0x78`（原实现） | 0 | **0** | —— | 数据里根本没这个值 |
| **分期字段被填（本实现）** | 648 | 4 | 61 / 277 / 37 / 378 分钟 | 心率有值率 **89~100%**、步数非零 ≤1 分钟、深睡 21~27% / REM 9~18% ✓ |
| `byte5`(浅睡强度) != 0 | 1136 | 7 | 多出 3 段 | 多出来的 3 段**心率 0%、有步数** → 白天假睡眠 ✗ |
| 低半字节 ∈ {9, 11}（GB 式） | 75 | 3 | 与上面同一批睡眠段 | 心率有值率 75~98%，边缘靠「继承上一个类型」补，偏松 |

「心率有值率」是最硬的旁证：**手环只在睡眠时每分钟测心率**，其余时候绝大多数分钟是 `0xff`（未测到），
所以判据的正确性可以用它交叉验证。分期被判据覆盖的分钟里心率 89~100% 有值，且步数为 0 —— 这两条
同时成立，说明归并出的就是真实的睡眠段，不是数据噪声。

## 3. 抓取逻辑（2026-09-15 修复，保留）

`syncActivity` 原来一轮只 `fetchActivityRound` 一块就返回，只能拿到最老的那块。参照
`AbstractRepeatingFetchOperation` 新增 `fetchActivityBlocks`：顺着块尾一块块要下去，直到手环回
`expectedBytes == 0` 或追上当前时刻，最后**一次性**把全量样本归并成夜（跨块边界的一觉不会被切碎）。
实测单次可拉满 **10075 分钟（09-08 → 09-15）**。

一次取数协议（照 `AbstractFetchOperation` 抄，字节级一致）：

| 步骤 | 内容 |
| --- | --- |
| ① | `00000004` 写 `01 01 + 时间8字节`（含时区，15 分钟一档） |
| ② | 手环 → `10 01 01 <采样数 u32le> <起始时间 8B>`；**这个 u32 是采样条数**（3216 × 8 = 25728 字节，实测分毫不差） |
| ③ | 订阅 `00000005`，写 `02` |
| ④ | `00000005` 推样本：每包首字节是递增序号，其余全是样本数据。**每包长度不固定**（实测 17B = 序号 + 2 个样本） |
| ⑤ | 手环 → `10 02 01`（传完） |
| ⑥ | 写 `03` = ACK。**我们不发**（GB 也有同样的开关 `keepActivityDataOnDevice`）|

## 4. 上一版结论为什么是错的（重要，避免再走回头路）

2026-09-15 的结论是「数据被官方 App 抢占并删除，手环端没有睡眠可给」，并据此写了「单一 App 接管 /
睡醒首发同步」等方案。**这个结论不成立**：

1. **手环没删数据**：2026-09-16 取数时，手环仍把 **09-09（6.8 天前）** 的数据完整推了过来；
   这期间官方 App 一直在正常同步。所以「官方 App ack 后手环删掉、第三方再也拿不到」是错的。
2. **同一份数据用对判据就能出 4 夜**：数据里睡眠分期一直都在，只是判据看错了字段。
3. **看走眼的具体原因**：当时诊断日志打印分期字节时先做了 `& 0x7f`
   （`"d%02x"` 打的是 `deepLevel`），**把「清醒 = 0x80」和「强度真的是 0」混成了同一个 `00`**，
   于是一眼看过去「夜里全是 00，白天才有值」，得出了「这些字段不是睡眠分期」的错误推论。
   现在诊断日志改成打印**原始字节**。
4. 另外，当时把「0x78 在 GB 里表示睡眠」直接搬到 MB5 上，没有核对
   `HuamiExtendedSampleProvider` 到底被哪些机型使用 —— 这正是 §2 的第 1 条。

**教训：结论落到「数据没有」之前，先把"看到的数据"本身打印成原始字节再确认一遍；
`& 0x7f` / `coerce` / 任何掩码都可能把有意义的哨兵值抹掉。**

## 5. 复现与自查（下次改协议照这个来）

实验台（debug 源集，release 里不存在）会把拉到的原始字节**落盘**并打印逐列取值分布：

```bash
bash tools/gradle.sh assembleDebug
bash tools/android_install.sh app/build/outputs/apk/debug/app-debug.apk
adb shell am start -n com.ted.shouhuan/.debug.ActivityLabActivity \
    --es mac <MAC> --es key <AuthKey> --ei days 7
adb logcat -s ActivityLab
adb pull /storage/emulated/0/Android/data/com.ted.shouhuan/files/activity_dump.bin app/build/
adb pull /storage/emulated/0/Android/data/com.ted.shouhuan/files/activity_dump.txt app/build/
python tools/analyze_activity_dump.py app/build/activity_dump.bin --meta app/build/activity_dump.txt
```

离线分析脚本会打印：逐列取值统计（哪一列像「类型」、哪一列像「强度/计数」）、逐列每小时均值、
每个取值的长连贯段落在几点、各「标记列」的连贯段，以及粗状态 RLE。
换 stride / 字段偏移、换判据都能在 PC 上秒试，不用改一次代码装一次包。

诊断日志里的关键行（`BandSession`）：
`判据睡眠分钟(isSleepMinute)=…`、`▷ 睡眠分钟按时段(0-23点)：…`、`░ 每晚情况…`。
